# Protocol

Technical reference for the DuoFern serial protocol as implemented by this integration. See the [main README](../README.md) for installation and configuration, and [Supported Devices & Features](devices.md) for the entity/device reference.

---

- **Frame format**: Fixed 22-byte (44 hex char) frames over UART at 115200 baud
- **Init sequence**: 7-step handshake (Init1 → Init2 → SetDongle → Init3 → SetPairs → InitEnd → StatusBroadcast)
- **ACK-gated send queue**: One command in-flight at a time, 5-second timeout. The stick acknowledges every command with `81 00 ...`; this only means the stick accepted it. For an unanswered status request the stick reports nothing further (no `810108AA`), so a silent device can only be recognised by the missing status frame
- **Startup status poll**: after the broadcast, devices of the FHEM poll list that have not sent a status frame are asked individually, one per second (the devices answer 0.2-0.3 s after the stick's ACK; back-to-back requests lost answers): a first round 30 s after startup, a second round 30 s later. Devices that still do not answer become unavailable; the list is stored (`.storage/duofern.<entry_id>.missing_status`) so that only these devices start as unavailable after the next restart. FHEM sends these requests without a pause
- **Exclusive serial port** (Home Assistant 2026.11+): Home Assistant opens serial ports exclusively. `disconnect()` therefore waits until the port is really released before a reload opens it again, and Reconfigure does not open the port the running integration is using
- **Push-based updates**: Devices send status frames proactively; coordinator calls `async_set_updated_data()` on each received frame
- **Position convention**: DuoFern 0 = open / 100 = closed; HA 0 = closed / 100 = open (inverted transparently)
- **HSA (Heizkörperantrieb)**: Device-initiated bidirectional protocol - changes are queued and transmitted only when the device checks in with a status frame, matching FHEM's `%commandsHSA` / `HSAold` implementation
- **HSA status frame** (format `29`): byte 4 bits 0-5 = desired-temp (raw `(r+8)/2` °C; during a boost the device reports 28.0 °C, byte 4 = `0xF0`, the same as a normal setpoint of 28.0 °C); byte 12: bit 7 = `forceResponse`, bit 6 = boost active, bits 0-5 = boost duration in minutes. Boost is detected from byte 12 bit 6 only
- **duoSetHSA**: `0D 01 1D 80 nn nn nn 00..00 [device code] 00`, `nnnnnn` = 24-bit `setValue`, big-endian (desired-temp raw `(t-4)/0.5` in bits 17-22, change flag bit 23). A change is sent with change flag 1 only if the device still reports the value it had when the change was queued
- **Boost frame layout** (OTA-verified via rtl_433):
  - ON: `f[8] = 0x40 | duration_min` (only if duration changed, else `0x00`), `f[11] = 0x03`; `sv` contains desired-temp only if it was changed, else `0x000000`
  - OFF: `f[8] = 0x00`, `f[11] = 0x02` (critical - `0x00` is silently ignored by the device)
- **Code-Pairing protocol** (OTA-verified via rtl_433):
  - USB frame byte 21 (flags) controls `pay[0]` in the radio frame: `0x00` = normal command, `0x01` = pairing mode
  - Sequence: SetPairs (0x03) → StartPair (0x04) → CodePair ×2 (`0D FF 06 01 ...`, flags=0x01) → wait for the `0602` response (or the device ACK `CC`) → StopPair (0x05) → store the 6-digit code, the config entry update reloads the integration
  - The stick must be in pairing mode (StartPair) before sending the pair frame
  - `f[1]=0xFF` required for correct radio payload mapping (`pay[7]=FF`)
  - 10-digit codes (devices since about 2020): the last 4 digits are a 2-byte pairing password, sent in clear text in USB bytes 4-5 (`0D FF 06 01 pw pw ...`; OTA: the two bytes after `0601`, `0000` for a 6-digit code). Nonce, repeat counter and the trailing 8-byte checksum of the radio frame are generated by the stick. Example: code `431234ABCD` = device `431234`, password `ABCD`. The device keeps its 6-digit identity
- **RolloTron obstacle detection** (status format `"21"`) - not in FHEM's `30_DUOFERN.pm` at all; FHEM's `%statusGroups{"21"}` has no obstacle/block field, and the word position Rohrmotor/SX5 use for it (word position 2) is already occupied here by `ventilatingPosition`/`ventilatingMode`. Derived from real device frames: word position 4, high byte, bit 7 (bit 15 of the 16-bit word) flips 0→1 when the device reports an obstacle. Confirmed against a single before/after frame pair from a RolloTron Comfort Master (`0x61`); no confirmed bit for blockage detection yet.

## Sniffing DuoFern Radio Frames (rtl_433)

To capture raw OTA frames with an RTL-SDR dongle (thanks a lot to gluap from pyduofern-hacs for writing down his command and pointing me to it):

```bash
rtl_433 -s 2.0M -f 434.5M -g 30 \
  -X "n=duofern,m=FSK_MC_ZEROBIT,s=10,r=100,preamble={10}fd4,invert" \
  -S known
```

Implementation based on `10_DUOFERNSTICK.pm` and `30_DUOFERN.pm` from the FHEM project.
